# Plan: stripped output under obj/ as static web assets (v0.3)

Tier: Standard. Status: approved 2026-10-15 with the decisions below. Written 2026-10-15 from SDK 10.0.401
targets and experiments in `tmp/objout/` (gitignored).

## Decisions (user, 2026-10-15)

1. Obj mode is the default for web projects; setting `PareOutDir` opts out.
2. A leftover sibling `foo.js`: warning PARE200, removed from Content, the build succeeds.
3. Scope: `wwwroot` sources only. Sources outside `wwwroot` and Razor class library `_content/`
   are later (`work/todo.md`); outside `wwwroot` they keep writing next to the source.
4. A source added during `dotnet watch` is 404 until the next build; the watcher logs a hint.

## Goal

In web projects, `Extrode.Pare.Build` writes each `wwwroot/**/*.ts` output to
`$(IntermediateOutputPath)pare/` and registers it as a static web asset, rather than
writing `foo.js` next to `foo.ts`. Results:

- Generated files never sit in the source tree, so no `.gitignore` is needed.
- A hand-written `foo.js` is never overwritten. It is reported instead.
- Build, run, publish (with `.br`/`.gz`) and `dotnet watch` hot reload behave the same as today.
- Outputs whose source was deleted are removed (item 2, folded in).

## Evidence

### SDK targets (10.0.401, `Sdks/Microsoft.NET.Sdk.StaticWebAssets/targets/`)

**Pipeline stages.** `Microsoft.NET.Sdk.StaticWebAssets.targets:296-320` defines three stages:
1. `ResolveCoreStaticWebAssets` holds files on disk. `ResolveProjectStaticWebAssets` runs
   `DefineStaticWebAssets` over `@(Content)` with `RelativePathPattern="wwwroot/**"` and
   `SourceType="Discovered"` (lines 697-740).
2. `ResolveStaticWebAssetsInputs` holds "assets generated by the build process, like scoped CSS".
3. `ResolveBuildRelatedStaticWebAssets` holds derived assets. Compression lives here.

**Prior art: scoped CSS.** `ScopedCss.targets:55-58` appends its target to
`ResolveStaticWebAssetsInputsDependsOn`. `_ComputeScopedCssStaticWebAssets` (lines 345-378) then:
- defines its files with `DefineStaticWebAssets`, using:
  - `SourceType="Computed"`
  - `ContentRoot="$(IntermediateOutputPath)scopedcss\"`
  - `BasePath="$(StaticWebAssetBasePath)"`
  - `AssetKind="All"`, `AssetMode="All"`, `AssetRole="Primary"`
  - `CopyToOutputDirectory="Never"`, `CopyToPublishDirectory="PreserveNewest"`
- defines their routes with `DefineStaticWebAssetEndpoints`;
- adds both to `@(StaticWebAsset)` and `@(StaticWebAssetEndpoint)` (lines 101-104).

**Compression.** `Compression.targets:185-260`: `ResolveBuildCompressedStaticWebAssets` runs inside
`ResolveBuildRelatedStaticWebAssetsDependsOn`, after the inputs stage, over all of
`@(StaticWebAsset)`. Assets added in the inputs stage are therefore compressed: gzip at build,
brotli and gzip at publish.

**Feature detection.** `UsingMicrosoftNETSdkStaticWebAssets=true` (`Sdk.StaticWebAssets.CurrentVersion.props:19`).

### Experiments (`tmp/objout/app`, a hand-written target copying `wwwroot/**/*.ts` to `obj/.../pare/**/*.js`)

| Check | Result |
|---|---|
| Build: dev manifest | `staticwebassets.development.json` lists `obj/Debug/net10.0/pare/` as a content root. `js/a.js` maps to it. |
| Build: endpoints | `js/a.js` and `js/a.js.gz` are in `staticwebassets.build.endpoints.json`. |
| `dotnet run`, Development, `MapStaticAssets` | `/js/a.js` returns 200 `text/javascript`. With `Accept-Encoding: gzip` it returns 200 gzip. |
| Rewrite the obj file while the app runs | The new content is served, with the new length and ETag, for plain and gzip requests. `StaticAssetDevelopmentRuntimeHandler` patches it at runtime. |
| `dotnet publish -c Release` | `wwwroot/` holds `index.html` and `js/a.js`, plus `.br` and `.gz` of each, and no `.ts`. |
| `dotnet watch` (hot reload) after editing the obj file | `File change: Update '.../obj/Debug/net10.0/pare/js/a.js'`, then `Sending static asset update request to connected browsers: 'wwwroot/js/a.js'`. This is the same message a `wwwroot` edit produces, so the browser refresh still fires. |
| Leftover `wwwroot/js/a.js` next to the obj output | Build error: `Conflicting assets with the same target path 'js/a#[.{fingerprint}]?.js'`. The error is loud, but its text is the SDK's. |
| New obj file created at runtime, plain `dotnet run` | 200 with the SDK's "not found in the built time manifest" warning. This needs a `StaticWebAssetDiscoveryPattern` for the obj root, which the experiment added. |
| New obj file created at runtime, under `dotnet watch` | **404** until the next build. A new `wwwroot` file is served in the same session. Adding the obj root to `WebRootFileProvider` did not change this. |
| Obj output deleted at runtime, Development | **500**: `FileNotFoundException` from `StaticAssetDevelopmentRuntimeHandler`. It falls back to a `wwwroot/` path. |

## Approach

### MSBuild (`src/Extrode.Pare.Build/build/Extrode.Pare.Build.targets`)

1. Mode selection: obj mode when `'$(UsingMicrosoftNETSdkStaticWebAssets)' == 'true'` and
   `'$(PareOutDir)' == ''`; otherwise today's behaviour (next to the source, or under
   `PareOutDir`). Non-web projects and an explicit `PareOutDir` are unchanged.
2. `_PareComputeOutputs`, in obj mode:
   - **Location.** Set `_PareOutRoot` to
     `$([MSBuild]::NormalizeDirectory('$(MSBuildProjectDirectory)', '$(IntermediateOutputPath)', 'pare'))`
     inside the target. At evaluation in a package `.props`, `IntermediateOutputPath` is not
     defined yet; the experiment hit this and wrote to `./pare/`.
   - **Routes.** Each `_PareSource` gets `PareOutputPath` (under `_PareOutRoot`) and
     `PareRelativePath`. The route comes from `%(PareRelativePath)` when set; otherwise from the
     path below `wwwroot/` for `wwwroot` sources; otherwise from the project-relative path. The
     last case makes sources outside `wwwroot` possible, for example `Scripts/**/*.ts`.
3. `PareStripTypeScript`: unchanged. Inputs and outputs are as today, and the `StripTypeScript` task
   already takes absolute `PareOutputPath`.
4. New `_PareDefineStaticWebAssets`, appended to `ResolveStaticWebAssetsInputsDependsOn` with
   `DependsOnTargets="ResolveStaticWebAssetsConfiguration;_PareComputeOutputs"`:
   - It defines the outputs with `DefineStaticWebAssets`, using the same arguments as scoped CSS
     plus `FingerprintCandidates`/`FingerprintPatterns`, so `.js` gets the same optional
     fingerprinted alternate as discovered assets. It defines their routes with
     `DefineStaticWebAssetEndpoints` and adds both to `StaticWebAsset`/`StaticWebAssetEndpoint`.
   - It adds a `StaticWebAssetDiscoveryPattern` (`**/*.js;**/*.mjs`) for the obj root, so files
     added at runtime are served under `dotnet run`.
   - `AssetMode="All"` with `BasePath="$(StaticWebAssetBasePath)"` means a Razor class library's
     outputs flow to referencing apps under `_content/<PackageId>/`, which today's Content route
     already does.
5. `_PareRegisterOutputs`, in obj mode:
   - no `Content Include` of outputs;
   - remove sources from `Content` (as today);
   - report each `wwwroot` sibling (`foo.js` next to `foo.ts`) as `warning PARE200: wwwroot/js/foo.js
     is shadowed by the output of foo.ts; delete it`, and remove it from `Content` so the SDK
     conflict error does not fire. This handles upgrades from 0.2, whose generated `.js` files
     are still on disk.
6. Stale outputs (item 2): after the strip, delete files under `_PareOutRoot` that no current
   source produces. This is safe because Pare owns that directory. All outputs stay in
   `FileWrites`, so `dotnet clean` removes them. Sibling mode keeps today's behaviour (no
   deletion), because a hand-written file there cannot be told apart.
7. Development map: when not publishing (`'$(_IsPublishing)' != 'true'`), write
   `$(OutDir)Extrode.Pare.development.json` with `WriteLinesToFile` and `WriteOnlyWhenDifferent`,
   and add it to `FileWrites`. It holds the source root, output root, include/exclude rules and
   each source-to-output pair. It is not Content, so publish never copies it.

### ASP.NET Core (`src/Extrode.Pare.AspNetCore`)

1. `PareDevelopmentService.StartAsync` reads `Extrode.Pare.development.json` from
   `AppContext.BaseDirectory` with `JsonDocument` (no reflection serializer; Development only).
   - If the file is present, `TypeScriptWatcher` takes the output root and the pairs from it. The
     build is then the one source of the path rules, and the watcher's copy of the glob plus
     `OutDir` can go.
   - If it is absent (a package older than 0.3, or a non-Web-SDK build), fall back to today's
     glob and next-to-source behaviour.
2. The watcher writes into the obj root. The experiment shows `dotnet watch` picks that up and
   refreshes the browser.
3. A new source added during `dotnet watch` produces a file that is 404 until the next build.
   The watcher logs once: `Stripped <src> to <out>; new files are served after the next build
   (Ctrl+R in dotnet watch)`.
4. A deleted source: the watcher deletes its obj output. A request for it then returns 500 in
   Development (SDK behaviour, see Evidence) until the next build. This is acceptable: no page
   should still import it. It goes in the README.
5. `PareDevelopmentOptions.OutDir`: `[Obsolete]`, used only for the fallback.

- README, MSBuild section:

## Rejected alternatives

| Option | Why not |
|---|---|
| Keep writing next to the source; only add `.gitignore` guidance | Leaves the overwrite hazard and stale files. It is today's state. |
| Output under `obj/`, added as `Content` with `Link="wwwroot/..."` | `ResolveProjectStaticWebAssets` uses `RelativePathPattern="wwwroot/**"` against the item spec. A project-relative spec was needed for first-build discovery (progress.md, M6). A linked obj path relies on undocumented `Link` handling, while `DefineStaticWebAssets Computed` is the SDK's documented hook used by scoped CSS. |
| Hook `GenerateComputedBuildStaticWebAssetsDependsOn` instead | It works too, but scoped CSS defines its assets in the inputs stage and only bundles there. Using the inputs stage keeps compression ordering explicit. |
| `RuntimeHostConfigurationOption` carrying the obj path to the app | The absolute path lands in `runtimeconfig.json`, which is published. |
| Parse `<app>.staticwebassets.runtime.json` to find the obj root | It would match a content root by its directory name, which is fragile, and it does not give the source-to-output pairs. |
| Make the watcher's obj root servable through `WebRootFileProvider` | Tested: under `dotnet watch`, still 404. |

## Tests (same branch as the change; break-check each)

Unit (`tests/Extrode.Pare.Tests`):
- `DevelopmentWatcherTests`:
  - the watcher reads the development map: outputs go to its output root, and pairs from the map
    win over the glob;
  - the fallback without a map stays today's behaviour;
  - deleting a source deletes its obj output;
  - a new source logs the next-build message.
  - Break-checks: ignore the map → the output lands in `wwwroot` and the test fails; skip the
    delete → the test fails.

Integration (`tests/Extrode.Pare.Integration/BuildIntegrationTests.cs`), updated:
- `Strips_wwwroot_sources_and_skips_them_when_up_to_date`: the paths move to `obj/Debug/net10.0/pare/js/...`. Assert nothing is written in `wwwroot`.
- `Outputs_become_static_web_assets_once_on_the_first_and_later_builds`: assert one `js/app.js` endpoint whose asset is under the obj root, on the first and the second build.
- `Out_dir_keeps_the_relative_layout`: unchanged; `PareOutDir` opts out of obj mode.
- `Dotnet_watch_without_hot_reload_restrips_an_edited_source`: reads from the obj root.
- `Dotnet_watch_hot_reload_refreshes_the_browser_with_the_restripped_source`: the expected log line names the obj path. The browser must still reload with the new text. This is the decisive end-to-end check.
- Sample browser tests (Development, publish, NativeAOT, all three engines): unchanged assertions. Pass means routes and compression survive. `Sample_modules_run_outside_the_browser` reads from the obj root.

Integration, new:
- `A_sibling_js_is_reported_and_not_served`: put `wwwroot/app.js` next to `app.ts`, then build. Expect warning PARE200, no conflict error, and the obj output served. Break-check: drop the `Content Remove` → the SDK conflict error appears.
- `Deleting_a_source_removes_its_output`: build, delete `b.ts`, build again. The obj `b.js` is gone and its endpoint too. Break-check: skip the delete step.
- `Publish_never_carries_the_development_map`: the published output has no `Extrode.Pare.development.json`.
- `Razor_class_library_outputs_flow_to_the_app_under__content`: an RCL with `wwwroot/x.ts` is referenced by a web app. Expect `/_content/Lib/x.js` served. Optional; see the open decisions.
- `Non_web_projects_write_next_to_the_source`: a `Microsoft.NET.Sdk` project with explicit items behaves as today.

## Migration and compatibility

- Upgrading a 0.2 project: the old generated `wwwroot/**/*.js` files stay on disk. PARE200 names
  each one, and the build still succeeds and serves the new output. Deleting them and the
  `.gitignore` lines is the user's step.
- Nobody uses Pare yet: it is unreleased on nuget.org, and the repo is private. So obj mode can
  be the 0.3 default with no opt-in period. `PareOutDir` remains the escape hatch.
- Plain `.js` files the user writes in `wwwroot` without a `.ts` sibling are untouched and served
  as before.

## Risks

- **Unclear:** `StaticAssetDevelopmentRuntimeHandler` falls back to a `wwwroot/` path for a
  missing obj file (500). This is SDK behaviour and could change in later 10.0.x releases. It
  is covered by the deleted-source integration test only at build level.
- The dotnet watch new-file 404 is a regression from today's next-to-source mode, where the new
  file is served.
- `IntermediateOutputPath` varies with RID, `UseArtifactsOutput` and a custom
  `BaseIntermediateOutputPath`. The development map handles this for the watcher, and the
  integration tests should cover one `UseArtifactsOutput` case.
- Visual Studio design-time builds: `Design.targets` loads only inside VS, and Pare does not
  load there today. No change.

## Open decisions (user)

1. Default or opt-in? Recommended: obj mode is the default in web projects for 0.3, with
   `PareOutDir` as the opt-out. A separate `PareWriteNextToSource=true` switch is the
   alternative.
2. Leftover sibling `foo.js`: warn and ignore it (recommended), or fail the build?
3. Sources outside `wwwroot` (for example `Scripts/**/*.ts`, routed by project-relative path or
   `PareRelativePath`): include in 0.3, or later?
4. RCL `_content/` support and its test: include now (low cost: it falls out of
   `StaticWebAssetBasePath`) or leave it untested?
5. The dotnet watch new-file limitation: accept it with a log line (recommended), or look
   for a way to force a rebuild (`dotnet watch` treats `Watch` items as rebuild triggers only
   with `--no-hot-reload`)?
