# Plan 002: StripTypeScript under Visual Studio's MSBuild

Status: done, 2026-10-15, on `feat/vs-msbuild` (option a, with the Windows-only integration test). Spike: `feat/vs-msbuild-spike` (6f726fb).

## Goal

`Extrode.Pare.Build` strips and registers `obj/` output when the project is built by Visual
Studio's MSBuild (.NET Framework, `MSBuild.exe`), not only by `dotnet build`, with no warning.

## Findings (wp1: VS 18 Community, MSBuild 18.10.1.42706, SDK 10.0.401)

- The .NET 10 SDK requires MSBuild 18.0 or later (`sdk/10.0.401/minimumMSBuildVersion` is
  `18.0.0`). Visual Studio 2022 (MSBuild 17) cannot build a net10.0 project with this SDK at all,
  so only MSBuild 18 needs support.
- **Today it already works, with a warning.** MSBuild 18.10 falls back to running the net10.0 task
  out of process and prints, once per build:
  `MSBUILD : warning : The custom task 'Extrode.Pare.Build' required a fallback to out-of-process
  execution because the UsingTask definition does not specify the correct Runtime and
  Architecture. This reduces build performance. Update the UsingTask element to explicitly specify
  Runtime and Architecture attributes (e.g., Runtime="CLR4" Architecture="x64") or use
  TaskFactory="TaskHostFactory".`
  Output was correct and registered as a static web asset. Earlier MSBuild 18 builds may not have
  this fallback; the documented mechanism is the explicit `UsingTask` below.
- Microsoft's documentation for .NET 10 / Visual Studio 2026: declare `Runtime="NET"
  TaskFactory="TaskHostFactory"` on the `UsingTask`, conditioned on `$(MSBuildRuntimeType)`
  `Full`, and keep the in-process declaration for `Core`. The .NET task always runs in a separate
  process under `MSBuild.exe`. Host objects are not supported out of process; the task uses none.

## Options

| Option | Result | Verdict |
|---|---|---|
| (a) .NET task host: two `UsingTask`s, `Runtime="NET" TaskFactory="TaskHostFactory"` when not Core | Spike: works, no warning, same timings | **Chosen** |
| (b) Multi-target core + task to netstandard2.0 / net472 | Core uses `ReadOnlySpan`/`Span` (19 sites), `ArrayPool` (6) and `SearchValues` (10). netstandard2.0 needs the System.Memory and System.Buffers packages (core must have zero packages) and has no `SearchValues` (hot-path rewrite, slower). | Rejected |
| (c) `Exec` the `pare` CLI under `MSBuild.exe` | Needs Windows binaries (x64 + arm64, ~2.7 MB) or a framework-dependent host in the package, a second code path for diagnostics (canonical error parsing) and for incremental inputs. | Rejected: more code for what (a) gives free |

| Check | Result |
|---|---|
| Build 1 / no-op build 2 | exit 0, 6.3 s / 2.6 s (baseline with the fallback warning: 6.2 s / 2.5 s) |
| Warning | none (baseline: the fallback warning above) |

## Not covered by the spike

- The Visual Studio IDE itself (devenv build, design-time builds). Over ssh only `MSBuild.exe` was
  run. Design-time builds do not run `BeforeBuild`, so they should not start the task host; an IDE
  build runs the same targets as `MSBuild.exe`. Check once by hand in VS on a desktop session.
- Node reuse: with `-nr:true` (the IDE default) the task host may stay alive between builds and
  hold the task dll open from the NuGet package folder, which never changes for a version. Updating
  the package version loads the new path.
- Hot reload from the IDE uses `AddPareDevelopment`, which does not depend on MSBuild; unaffected.

## Risks

- MSBuild 18.0 to 18.9 without the automatic fallback: covered by the explicit `UsingTask`, which
  the docs give for all of .NET 10 / VS 2026; not tested on such a build.
- The task host starts the .NET runtime per build (out of process); measured cost is within noise
  (6.3 s vs 6.2 s).
