# 001: Core input is UTF-16 (`ReadOnlySpan<char>`)

Date: 2026-10-14. Status: accepted (M0).

## Decision

`TypeStripper.Strip` takes `ReadOnlySpan<char>` and writes to `IBufferWriter<char>`. A UTF-8
entry point, if needed by the MSBuild task or middleware, transcodes in and out through pooled
buffers around the same core.

## Why

- **The position invariant is defined in UTF-16 code units.** JS engines report columns in
  UTF-16 units. Erasing in UTF-16 is one space per code unit and the invariant holds by
  construction. In UTF-8, a non-ASCII character inside a type (`type A = "é"`) would need one
  space per UTF-16 unit, not per byte, so the eraser would need decoding logic anyway.
- **Simpler lexer.** Identifiers may use any Unicode ID_Start/ID_Continue character. With `char`
  the common path is a table lookup and the rare path is `char.IsLetter` plus surrogate pairs;
  with bytes every non-ASCII byte needs decoding first.
- **Tests and tooling speak strings.** Acornima, diagnostics and `SourceLocation` all take
  `string`/`char` spans.
- **Transcoding is cheap relative to recognition.** `Encoding.UTF8` is vectorized and runs at
  several GB/s; the recognizer will not. Pooled transcode buffers keep it allocation-free.

## Cost

- Twice the memory bandwidth of UTF-8 on ASCII input.
- Two transcodes per file in the MSBuild path. Revisit in M7 if benchmarks show transcoding
  above roughly 10% of `Strip` time.
